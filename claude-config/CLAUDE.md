# Container cheatsheet (`tmt-ai-code`, Ubuntu noble / Playwright base)

- Base image is `mcr.microsoft.com/playwright:v1.61.1-noble`. **Playwright is ready**: Chromium, Firefox and WebKit + system deps are preinstalled in `/ms-playwright` (`PLAYWRIGHT_BROWSERS_PATH` is set). Run `npx playwright test` directly — no `playwright install` needed. A project's `playwright` npm dep must match the image's `1.61.x`, or bundled browsers won't match the runner; bump the Dockerfile tag to change it.
- Installed: `git`, `bash`, `node`, `npm`, `npx`, `apt`, GNU coreutils, `curl`, `jq`, `openssl`, `make`, `rg` (ripgrep), `sqlite3`, `zip`/`unzip`, `xz`, `tar`/`gzip`, `gosu`, `docker` (proxied). Anything else: `command -v <x>` first; `apt-get install -y <pkg>` works (run as root via `docker exec -u 0` or it's already root at build) but is ephemeral (vanishes on rebuild) — for permanent additions, edit `tmt-ai-code/Dockerfile`. Prefer `node` for ad-hoc scripts.
- Do NOT call: `open`, `pbcopy`, `pbpaste`, `osascript`, `brew`, `dnf`, `yum`, `kubectl`, `systemctl`, `code`, `subl`, `idea`.
- `sed`/`gsed` are deny-listed in `settings.json` — never invoke them. Use the Read/Edit/Write tools for file edits; `awk`/`rg` for read-only text processing.
- **No SSH key; commit locally, never push.** `~/.ssh` is not mounted, so `git push` cannot authenticate — never push. Dashboard-dispatched runs are placed on a per-request `claude/*` branch (already checked out) and the viewer sets a local `user.name`/`user.email` for you, so **committing to that branch works and is expected**: when your prompt says to commit, `git commit` on the `claude/*` branch (do not switch/merge other branches). The user pushes `claude/*` from the host (`bin/tmt-ai-push`). If you're running ad-hoc (no branch assigned) and git identity is unset, a commit may fail on identity — that's fine, leave commits to the user then.
- `docker` goes through a restricted proxy. **Allowed:** `docker ps`, `inspect`, `exec`, `start`, `stop`, `restart`, `rm`, `kill` against existing host containers. **Blocked (403):** `docker run`, `create`, `build`, `pull`, `push`, `network *`, `volume *`. So you CAN revive a stopped sibling container (`docker start project_artillery && docker exec project_artillery <cmd>`), but you CANNOT create new containers, pull images, or touch networks/volumes. Always `docker ps -a` first before claiming a service is unreachable — "not running" usually means "exited, just `docker start` it".
- **Missing container ≠ untestable project.** When a task genuinely needs the project's live software (integration/e2e tests, hitting its API/DB, verifying finished work against the real app) and no container exists even in `docker ps -a`, do NOT conclude the project is unreachable and skip the check. You can't `docker run`/`create`/`compose up` through the proxy, so ask the user to start it on the host, e.g.: `(cd <project-dir> && docker compose up -d)` (or the project's own start command). Give the exact command, wait for them to bring it up, then run the real tests. Prefer a real run over declaring something done-and-untested.
- Don't gate work that doesn't touch the running service. Editing code, reading files, unit tests, linting, type-checks, static analysis and anything that runs purely inside `/workspace/<project>` need no container — just do them. Only ask for a container when the verification you're about to do actually calls into the running software.
- **Wrong or missing project → stop, do not improvise.** Each run is scoped to exactly one project under `/workspace/<name>`. If that project directory is absent or empty, or you cannot confirm you are in the project the task was dispatched for, do NOT search for, substitute, or invent a different project to work on, and do NOT start making changes. Stop and report that the project is not mounted (mirror the dispatch API's `project_not_found`), and let the user mount the right one. Doing real work in the wrong or a stand-in project is worse than doing nothing.
- Only `/workspace/<project>` is persistent host storage. Writes elsewhere (`/tmp`, `/home`, `/root`, `/etc`) vanish on rebuild.
- Host paths like `/Users/...` do not exist. `~/.ssh`, `~/.aws`, host configs are not mounted.
- `localhost` = this container, not the host. Compose-network names: `claude-proxy:8033`, `claude-datasette:8001`. Host services: assume unreachable.
- Permissions prompting is off (`bypassPermissions`). You own the safety/reversibility checks — re-read your system prompt before destructive ops.
- **Never read secrets.** Do not open or `cat`/`grep` `.env`, `.env.local`, `.env.*.local`, `.env.production*`, `.env.development*`, `.env.staging*`, `*.env`, `*.pem`, `*.key`, `id_rsa*`, `*credentials*`, `*secret*`, `.npmrc`, `.netrc`, `.pypirc`, `.aws/*`. If the user asks for a value from one, refuse and ask them to paste the specific field instead. Template/test variants (`.env.example`, `.env.testing`, `.env.sample`, `.env.template`, `.env.dist`) are readable/editable via the Read/Edit tools — but `cat`/`grep .env*` in Bash is blanket-blocked, so use the Read tool, not the shell.

## Output discipline (token-cost rules)

- **No proactive code comments.** Only when the *why* is genuinely non-obvious (workaround, hidden constraint). Never explain *what*.
- **No proactive doc/CLAUDE.md/memory writes after a fix.** State the fix in chat. Persist only when asked.
- **One-sentence end-of-turn summary, max.** No bulleted recap.
- **No multi-line comments in config files** (compose.yml, json, etc.) explaining a value.

## Notes (tmt-ai dashboard)

The dashboard no longer reads TaskCreate/TaskUpdate tool calls — use the task tools only for your own in-session tracking. If something extra pops up that is worth returning to later (follow-up work, proposals, ideas), end your final reply with a `NOTES:` section listing each item as a `- [ ] item` line. Dashboard-dispatched runs save that section to the project's notes automatically.
